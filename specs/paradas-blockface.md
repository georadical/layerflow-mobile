# Reference — BlockFace & Paradas (app consumes later, read-only)

Status: reference note, NOT an app spec yet. The app produces nothing and,
today, consumes nothing of this. It is the backend's pinned model for the
"paradas" reference layer, recorded here so the future app-side paradas spec
builds against these decisions (relayed by the backend 2026-09-18).

## What it is
A reference layer that scopes each address to an **ordered block face** (cara
de manzana). Generated by the GIS engineer in QGIS → PostGIS; the app's
write-path stays coordinate-free — this geometry is read-only reference data.

## The model (backend-owned)
- **Two entities, not one:**
  - `block_faces` — spatial, route-AGNOSTIC: the real face. One point per
    face (snapped to the block polygon), inherits `manzana_catastral`, stores
    POINT geometry (MAGNA-SIRGAS) and a stable identity (UUID) + a canonical
    `face_index`.
  - `route_block_faces` — the **parada**, route-SCOPED: which route covers a
    face and in what walk order (`face_sequence`).
- **`face_index` is canonical and deterministic** (the surveyor never assigns
  it): bearing block-centroid→face; the face nearest North = 1, the rest
  clockwise, ties broken East. Reproducible and stable across re-censuses;
  works for blocks of 1..n faces (irregular included).
- **A manzana may split across routes** with no clash: Route A covers some
  faces, Route B others, over the SAME shared `block_faces`.
  `manzana_catastral` is never a route key or lock. Routes split on whole
  faces; the model tolerates one face split between two routes (a valve).
- **Census link:** `census_codes.block_face_id` (nullable FK) → the physical
  face (not the parada); the route context comes from `census_code.route_id`.
  **Null = pending snap, a valid state, not an error.**

## What is NOT the app's work
- No capture/edit of faces, paradas or their geometry (all in QGIS → PostGIS).
- No computing `face_index`, no snapping.
- The app does NOT send `block_face_id` in the sync — the ingest populates it;
  if the app ever sent it, it would be respected, but it is not required.
- The write-path stays coordinate-free; this is reference data only.

## What the app WILL consume (when ready — NOT built yet)
Two read-only endpoints, backend tickets **TP.4 / TP.5** (contract to come):
- Faces by manzana, ordered by `face_index`.
- Paradas by route, ordered by `face_sequence`.

Once they exist, the app-side paradas feature is: a **parada selector /
advance** (walk the route in `face_sequence`), and **auto-scoping** the
typeahead/capture to the current parada's manzana. The R1 typeahead is already
manzana-scoped (CL-R1 v1.2, built to "be fed by paradas with zero change") and
the manzana field is already kept per block — so the plumbing is partly there;
what is missing is consuming the contract and the parada UI. That becomes its
own spec (Spec → wireframe → design → impl) when TP.4/TP.5 land.

## Out of scope (later features)
- Geocoding QC (flagging a predio whose address does not fall on its face).
- Cross-census matching.

## In short
Today the app changes nothing. When integrated: read-only paradas/faces per
route; each face's identity is its canonical `face_index`; a manzana shared
between routes is supported, not a conflict.
