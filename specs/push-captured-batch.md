# Spec 3 — Push the captured batch

Status: draft, awaiting approval
Type: Mobile app (Flutter). No backend work: `POST /field/capture/placas` is
built and in use.
Chain: Spec 1 → 1.1 → **3 (this one)** → 4 offline-first queue and retry.

## User story
**As** a field worker finishing a stretch of a route, **I want** what I
captured to reach the office and to see clearly what did not and why, **so
that** I can leave knowing I am not carrying work stuck on my phone.

## Goal
Make the queue legible and sending deliberate. The transport already works;
what is missing is that the worker can see the queue where it matters, send it
on purpose, and understand a partial failure.

## Background — what is wrong today
- **The send control is in the wrong screen.** It is an icon in the capture
  form's app bar, while the resume view is where the worker sees which rows
  read "sin enviar" and offers no way to send them.
- **Sending happens by itself.** Saving a capture pushes the queue silently,
  so an edit made earlier can reach the backend without the worker doing
  anything they would recognise as sending.
- **A rejected row is indistinguishable from a queued one.** Both render the
  "sin enviar" badge. `syncError` is stored and never shown, so an item the
  server refused looks exactly like one that simply has not been sent.

## Scope

**Includes**
- **One** send control, on the resume view, showing how many rows are pending.
  The capture screen's sync icon is removed: the queue is seen and acted on in
  a single place, the same rule Spec 1.1 applied to the two lists.
- **Nothing sends by itself.** Auto-sync on save is removed; every push is a
  deliberate action.
- **Retry is manual.** Regaining signal does not trigger anything.
- Distinct treatment for `error` and `pending`, and the server's reason shown
  for a failed row.
- Partial-success reporting: how many were sent, how many failed, and which.
- Error mapping for the push itself: 401, 403, 404, no connection.

**Does NOT include**
- Any backend change.
- Automatic retry, backoff, or background sending — a deliberate choice, not
  an omission (see BR1).
- Re-pulling the frame after a push. The POST response already carries `id`,
  `loc` and `status` per item, so a second request would only duplicate what
  the app already knows. The worker can pull to refresh whenever they want to
  confirm against the server.
- Chunking a large queue into several batches (see BR5).
- Deleting or reordering units, and the observation layer (`/sync/*`).

## Actors and permissions
Field worker with the same `field_token`. The route must belong to their ESP.

## Preconditions
At least one row of the route is `pending` or `error`, and there is
connectivity.

## Wire contract consumed (source of truth — do not change from the app)
`POST /field/capture/placas`
```json
{ "route_id": "<uuid>", "batch_id": "<uuid generated by the app>",
  "items": [ { "client_id": "<uuid per unit, stable across retries>",
               "orden": 1, "placa": "12-34", "manzana_catastral": "001",
               "tipo_acceso": "porton", "observacion": "texto" } ] }
```
Response: `{ batch_id, route_id, total, created, updated, errores,
items:[{client_id, ok, id, loc, status}] }`.

- Idempotent by `client_id`: re-sending updates, never duplicates.
- Per-item SAVEPOINT: one bad item does not abort the batch.
- Errors: 401 (missing/invalid token), 403 (not a field token), 404 (route of
  another ESP or nonexistent), 400 (invalid `route_id`, `client_id` or
  `orden`).

## Trigger
The worker taps the send control on the resume view.

## Main flow (happy path)
1. The resume view shows how many rows are waiting, e.g. "3 sin enviar".
2. The worker **taps send**.
3. The app builds one batch with every `pending` and `error` row of the route,
   a fresh `batch_id`, and each row's own `client_id`.
4. While it is in flight the control shows progress and cannot be tapped
   again.
5. Every item comes back `ok`: each row is marked `synced` with the `loc` and
   the `id` the server assigned, the badges disappear, and the result is
   reported as "3 enviadas".

## Alternative flows (sad paths)
- **A1 — Partial success**: some items come back `ok` and some do not. The
  successful rows are marked `synced`; the failed ones move to `error`
  carrying the server's reason. The report says how many of each, and it is
  not treated as a failed push.
- **A2 — Duplicate `orden` in the route**: the server rejects that item and
  accepts the rest. The row shows its reason so the worker can see the
  collision instead of guessing.
- **A3 — No connection**: the control is disabled and says so. The queue is
  untouched. Nothing is attempted.
- **A4 — Connection lost mid-push**: nothing is marked `synced`; the whole
  batch stays queued. Re-sending is safe because `client_id` is stable, so the
  worst case is the backend updating rows it already had.
- **A5 — 401 or 403**: the copy and the action match the rest of the app
  ("renuévalo en Ajustes" / "pide un field_token al operador"). The queue is
  preserved: a credentials problem must never cost captured work.
- **A6 — 404**: the route is not visible to this token. The queue is
  preserved; the worker is told to go back to Mis rutas.
- **A7 — Nothing to send**: the control is inert and says there is nothing
  pending, rather than firing an empty request.
- **A8 — Retrying a failed row**: pressing send again includes rows in `error`
  along with `pending` ones. There is no separate "retry" gesture.

## Business rules
- **BR1** **Nothing sends by itself.** Every push is triggered by the worker,
  and so is every retry. Regaining signal changes nothing. In the field,
  invisible writes to real data are worse than a queue that waits.
- **BR2** The queue belongs to the **route**, not to the capture form, and
  there is exactly **one** send control in the app: on the resume view, where
  the queue is visible. Seeing the state in one screen and acting on it in
  another is the split Spec 1.1 removed; a second button would rebuild it.
- **BR3** `pending` and `error` are different states and must look different.
  A row the server refused is not a row waiting its turn.
- **BR4** Idempotency is the app's safety net: `client_id` is stable per unit,
  so any re-send updates in place. The app never tries to work out "what
  changed".
- **BR5** One batch per push, with everything queued for that route. No
  chunking until there is evidence it is needed; the backend already handles
  per-item failure.
- **BR6** A push failure never loses local work. Rows only leave the queue
  when the server confirms them item by item.
- **BR7** A new `batch_id` per attempt, so each attempt is auditable on the
  backend.
- **BR8** Coordinate-free: the payload carries no coordinates.

## Edge cases and error handling
- A row with `placa = null` is valid and is sent as null (contract A4).
- A row edited twice before any push is sent once, with its latest values.
- The response omits an item the app sent: that row is treated as failed and
  stays queued, never silently marked `synced`.
- `errores > 0` with `items` all `ok` — trust the per-item results, which are
  what the app acts on.
- A queue of hundreds: one request. If that turns out to hurt in the field,
  chunking is Spec 4, with evidence.
- Pressing send twice quickly must not produce two batches in flight.

## Acceptance criteria
- The resume view shows the pending count and can send from there, and it is
  the only send control in the app.
- The capture screen no longer carries a sync icon.
- Saving a capture no longer sends anything by itself.
- Sending reports how many went and how many failed.
- A failed row is visually distinct from a queued one, and its reason is
  reachable.
- Pressing send again retries the failed rows, and re-sending never creates
  duplicates.
- 401, 403, 404 and loss of connection all leave the queue intact.
- With nothing pending, the control does not fire a request.
- `flutter test` green, plus a manual check on route 10: capture with no
  connection, restore it, send, and confirm the rows land.

## BDD (Gherkin)
```gherkin
Feature: Push the captured batch

  Scenario: Send everything that is queued
    Given a route with 3 rows marked "sin enviar"
    When the worker taps send and every item comes back ok
    Then the 3 rows are marked synced with the loc the server assigned
    And the report reads 3 enviadas

  Scenario: Nothing is sent without being asked
    Given a route with queued rows
    When the worker saves a new capture
    Then nothing is sent
    And the queue still shows the rows as "sin enviar"

  Scenario: Partial success
    Given a batch where one item is rejected for a duplicate orden
    When the push completes
    Then the accepted rows are marked synced
    And the rejected row is marked as failed with the server's reason
    And the report states how many succeeded and how many failed

  Scenario: A failed row does not look like a queued one
    Given a row rejected by the server
    When the worker looks at the route
    Then that row is distinguishable from rows that are merely waiting
    And its reason can be read

  Scenario: Retrying does not duplicate
    Given a row that failed and was corrected
    When the worker taps send again
    Then it travels with the same client_id
    And the backend updates the existing unit instead of creating another

  Scenario: Expired token during a push
    Given a field_token that expired
    When the worker taps send
    Then the API answers 401
    And the queue is left untouched
    And the app points at Ajustes

  Scenario: No connection
    Given no connectivity
    When the worker looks at the send control
    Then it is disabled and explains why
    And no request is attempted
```

## Suggested tickets
- **T3.1 — Send control on the resume view**: pending count plus the action,
  with its disabled and in-flight states.
- **T3.2 — Remove auto-sync and the second control**: saving a capture no
  longer pushes (BR1), and the capture screen's sync icon goes away (BR2).
- **T3.3 — Distinguish `error` from `pending`** in the list and expose the
  server's reason for the row (BR3).
- **T3.4 — Report the outcome**: how many sent, how many failed, mapping 401,
  403, 404 and no connection.
- **T3.5 — Guard against double-send**: one batch in flight at a time.
- **T3.6 — Tests**: partial success, an item missing from the response, and
  the queue surviving each failure mode.
- **T3.7 — Manual check** on route 10: capture offline, restore connection,
  send, confirm.
